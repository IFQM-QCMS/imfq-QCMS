1. Executive Summary & Enterprise Business Context

QCMS (Quality & Continuous Improvement Management System) is an enterprise SaaS platform engineered to digitize, automate, and enforce structured problem-solving methodologies—principally 8D (Eight Disciplines) and Six Sigma. Large-scale manufacturing, automotive, aerospace, and electronics enterprises utilize QCMS as their central "Quality Operating System".

In an enterprise environment, corporate IT security mandates that users never maintain disconnected local passwords. Authentication must be delegated to corporate Identity Providers (IdPs) via Single Sign-On (SSO). This delivers four paramount security guarantees:

  • Centralized Access Governance & Offboarding: When an employee is deactivated in Microsoft Entra ID or Okta, their access to QCMS is instantly revoked across all active sessions.
  • Conditional Access & MFA Enforcement: QCMS automatically inherits corporate multi-factor authentication, device compliance checks, and geo-fencing policies.
  • Zero Password Transit & Hash Exposure: No passwords reside in or transit through the QCMS database for SSO accounts.
  • Just-In-Time (JIT) Provisioning: Automated account instantiation, plant assignment, department mapping, and role assignment upon first corporate login.
Enterprise Architecture Objective
This document outlines the complete architectural topology of QCMS, maps the relational connections between all 131 database entities (specifically identity, organizations, plants, departments, sessions, and workflows), and provides the full engineering blueprint to configure and deploy production-grade SSO.

2. QCMS Software Architecture & Multi-Tenant Topology

QCMS is designed around a high-performance modular topology combining a lightweight Single Page Application frontend with an asynchronous Flask backend and a serverless PostgreSQL relational database.

2.1 Multi-Tenancy Architecture

QCMS employs a Shared Database, Shared Schema, Row-Level Isolation model:

  • Tenant Context (org_id): Every organization is isolated by an integer org_id foreign key stamped across all core transactional entities (users, departments, plants, projects, audit_logs, sops).
  • Platform Separation: Platform-level SuperAdmins operate across organizations or have org_id = NULL (or belong to a dedicated platform organization marked with is_platform_org = True).
  • Granular 6-Tier RBAC Hierarchy:
    1. SuperAdmin (Level 5): Platform owner, billing, global configurations, cross-tenant auditing.
    2. Admin (Level 4): Organization owner, manages users, departments, plants, and tenant SSO configurations.
    3. Reviewer (Level 3): Mandatory sign-off authority for critical quality stage transition gates (Stages 4, 5, 7, 8).
    4. Facilitator (Level 2): Technical RCA and 7 QC Tools validator.
    5. Team Leader (Level 1): Project manager, responsible for project execution and team coordination.
    6. Team Member (Level 0): Core contributor, responsible for data entry and action execution.
    7. CEO: Executive stakeholder with read-only visibility, stage sign-off, analytics, and audit oversight.

4. Current Authentication System & SSO Gap Analysis

In the current QCMS implementation, authentication is handled in backend/app/presentation/routes/auth_routes.py via /login and /login-config:

  1. Identifier Resolution (GET /api/auth/login-config): Receives the user's typed identifier, resolves their organization, and returns available login options along with branding assets.
  2. Local Password Check (POST /api/auth/login): Verifies the identifier against Bcrypt password hash, enforces failed login locks, and issues a JWT signed with JWT_SECRET_KEY.
Architectural Gap in Commented-Out SSO Code
In auth_routes.py (lines 2205–2312), a commented-out stub for /api/auth/sso/<provider> accepted raw client-supplied JSON {{ email, token }} without cryptographically verifying the signature of the token against IdP JWKS public keys, lacked XML signature validation for SAML, and lacked multi-tenant corporate domain routing. This stub was intentionally deactivated.

5. Enterprise SSO Target Architecture (OIDC & SAML 2.0)

The enterprise target architecture introduces two distinct SSO tiers:

  • Platform SuperAdmin SSO: Authenticates internal DevOps, Security, and Support personnel via corporate Google Workspace or Microsoft Entra ID. Yields SuperAdmin privileges with org_id = NULL.
  • Tenant Enterprise SSO: Authenticates corporate employees of specific customers (e.g. Tata Motors, Mahindra, Bosch). Triggers automatically upon entering corporate email domains (e.g. @tatamotors.com) and enforces corporate Conditional Access and MFA.

6. OpenID Connect (OIDC) / Azure AD / Google Flow Deep-Dive

The OIDC flow utilizes the Authorization Code Grant with Proof Key for Code Exchange (PKCE):

  1. Discovery & PKCE Generation: The client initiates login; QCMS generates a cryptographically random code_verifier (SHA-256 hashed to code_challenge) and unique state stored in Redis.
  2. IdP Redirection: The user is redirected to Microsoft Entra ID or Google with parameters: client_id, redirect_uri, scope=openid profile email, state, and code_challenge.
  3. Corporate MFA Execution: The user signs in on their corporate portal, completing FIDO2 / Authenticator MFA.
  4. Back-Channel Token Exchange: IdP redirects to QCMS with code. QCMS calls IdP's /token endpoint directly (back-channel) passing the code_verifier.
  5. Cryptographic Verification: QCMS verifies the signed id_token against live JWKS public keys, ensuring valid issuer, audience, and future expiration.
  6. JIT Provisioning & Session Activation: The JIT engine creates/updates the user, generates a new SaaSUserSession, caches Redis presence, and returns the QCMS JWT.
Figure 4: SAML 2.0 Service Provider-Initiated Enterprise Federation Flow Sequence

7. SAML 2.0 Enterprise Federation Flow Deep-Dive

For enterprises utilizing Okta, Ping Identity, CyberArk, or on-premises ADFS, QCMS acts as a standard SAML 2.0 Service Provider (SP):

  1. SP Metadata Publishing: QCMS publishes standard SAML XML metadata at /api/auth/sso/saml/metadata/<provider_id> containing Entity ID, ACS URL, and public X.509 cert.
  2. Signed AuthnRequest Generation: QCMS generates a signed <samlp:AuthnRequest> and redirects the browser to the corporate IdP Single Sign-On URL.
  3. SAML Assertion Response: The IdP authenticates the user and generates a signed <samlp:Response> with an encrypted/signed <saml:Assertion>.
  4. ACS Processing & XML Signature Verification: The browser POSTs the SAML response to the QCMS ACS endpoint. The backend validates the XML digital signature against the stored IdP X.509 certificate, verifies NotBefore / NotOnOrAfter, extracts NameID and attribute claims, and provisions the user.
Figure 5: Multi-Tenant Corporate Domain Routing & Just-In-Time (JIT) User Provisioning Flowchart

8. Multi-Tenant Domain Routing & Just-In-Time (JIT) Provisioning Engine

When an employee signs in with corporate credentials for the first time, the JIT engine dynamically executes:

  • Tenant Org Matching: Matches the email domain (e.g. @tatamotors.com) to the owning organization in sso_providers.
  • Role Mapping: Translates IdP security groups (e.g. "QCMS-Reviewers") into the canonical QCMS role (Reviewer). Falls back to default_role_id (Team Member).
  • Plant & Department Auto-Resolution: Resolves IdP office location and department strings against existing records in plants and departments.
  • Credential Protection: Assigns an unusable randomized Bcrypt hash to the user's password record, guaranteeing that local password attacks are impossible.

10. Complete Backend Implementation Blueprint

The backend SSO subsystem is placed in backend/app/presentation/routes/sso_routes.py:

from flask import Blueprint, request, jsonify, redirect, current_app
from flask_jwt_extended import create_access_token, set_access_cookies
from app.infrastructure.database.models.models import db, User, Role, Organization, SaaSUserSession
from app.infrastructure.cache.redis_client import cache as redis_client
import requests
import secrets
import hashlib
import base64
from datetime import datetime, timezone, timedelta

sso_bp = Blueprint('sso', __name__, url_prefix='/api/auth/sso')

@sso_bp.route('/initiate', methods=['GET'])
def initiate_sso():
    provider_id = request.args.get('provider_id')
    email = request.args.get('email', '').strip().lower()
    
    from app.infrastructure.database.models.sso import SSOProvider
    provider = None
    if provider_id:
        provider = db.session.get(SSOProvider, int(provider_id))
    elif email and '@' in email:
        domain = email.split('@')[1]
        provider = SSOProvider.query.filter(
            SSOProvider.allowed_domains.contains([domain]),
            SSOProvider.is_active == True
        ).first()

    if not provider:
        return jsonify({"status": "error", "message": "No active SSO provider found."}), 404

    if provider.protocol == 'OIDC':
        # Generate PKCE verifier & challenge
        code_verifier = secrets.token_urlsafe(64)
        code_challenge = base64.urlsafe_b64encode(
            hashlib.sha256(code_verifier.encode('ascii')).digest()
        ).decode('ascii').rstrip('=')
        
        state = secrets.token_urlsafe(32)
        nonce = secrets.token_urlsafe(32)
        
        # Store state & verifier in Redis for 10 minutes
        redis_client.set(f"sso_state:{state}", json.dumps({
            "provider_id": provider.id,
            "code_verifier": code_verifier,
            "nonce": nonce
        }), ex=600)
        
        auth_url = (
            f"{provider.auth_endpoint}?"
            f"client_id={provider.client_id}&"
            f"response_type=code&"
            f"redirect_uri={request.host_url.rstrip('/')}/api/auth/sso/oidc/callback&"
            f"scope=openid profile email&"
            f"state={state}&"
            f"nonce={nonce}&"
            f"code_challenge={code_challenge}&"
            f"code_challenge_method=S256"
        )
        return redirect(auth_url)

    elif provider.protocol == 'SAML':
        # Redirect to SAML AuthnRequest generator
        return redirect(f"/api/auth/sso/saml/login/{provider.id}")

11. Enterprise Identity Provider Configuration Playbooks

11.1 Microsoft Entra ID (Azure AD) Setup

  1. Navigate to Microsoft Entra Admin Center (entra.microsoft.com) > App registrations > New registration.
  2. Set Name: QCMS Enterprise Quality System.
  3. Set Redirect URI (Web): https://qcms.company.com/api/auth/sso/oidc/callback.
  4. Under Certificates & secrets, generate a Client Secret.
  5. Under Token configuration, add Optional Claims: email, given_name, family_name, groups.
  6. Record Application (client) ID, Directory (tenant) ID, and Client Secret into the QCMS sso_providers record.

11.2 Okta SAML 2.0 Setup

  1. In Okta Admin Console, select Applications > Create App Integration > SAML 2.0.
  2. Set Single Sign-On URL: https://qcms.company.com/api/auth/sso/saml/acs/{org_id}.
  3. Set Audience URI (SP Entity ID): https://qcms.company.com/sp/saml/metadata.
  4. Map attributes: email -> user.email, name -> user.displayName, department -> user.department.
  5. Export Okta's X.509 Signing Certificate and store it in sso_providers.idp_x509_cert.

12. Security Hardening & Compliance Standards

Compliance Dimension Architectural Implementation & Control
ISO 27001 (A.9.4.2 User Authentication) Delegates credential lifecycle to corporate IdPs enforcing corporate password complexity, periodic rotation, and hardware MFA.
SOC 2 Type II (CC6.1 Access Control) All SSO assertions, session creations, attribute updates, and failed logins are written immutably to audit_logs with IP and User-Agent.
Replay Attack Prevention OIDC nonces and SAML InResponseTo identifiers are validated against Redis and deleted upon first use. Timestamps enforced with <300s skew.
Cryptographic Trust Only RS256 / SHA-256 signatures are accepted; deprecated SHA-1 digests are unconditionally rejected. Live JWKS public keys refreshed daily.
Single Logout (SLO) When an IdP sends an SLO notification, QCMS terminates the corresponding SaaSUserSession and removes the Redis key, revoking access immediately.
